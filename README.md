# Прогноз цены товара по табличным данным и выявление значимых факторов цены

Учебный проект по анализу данных на Python.

## 1. Цель и результат

**Цель:** по готовым таблицам с ценой и признаками (категория, бренд, регион и др.) построить модели прогноза цены и выявить факторы, которые на цену влияют значимо.

**Три итоговых артефакта:**

| # | Артефакт | Формат | Где лежит |
|---|---|---|---|
| 1 | Исходный код анализа | Python (`.py` / ноутбук) | `src/` |
| 2 | Отчёт | DOCX | `reports/report.docx` |
| 3 | Презентация | PPTX | `reports/presentation.pptx` |

## 2. Задачи (из задания)

1. Объединить таблицы.
2. Описательная статистика.
3. Гипотезы о влиянии категории / бренда / региона на цену.
4. Корреляция и VIF.
5. Регрессия: линейная, Ridge, квантильная.
6. Классификация ценового сегмента.

## 3. Датасеты

Рассматриваем 5 (требование: не менее 5 найдено, 1–3 выбрано и обосновано):

| Датасет | Что внутри | Предварительная оценка |
|---|---|---|
| **Olist** (Brazilian E-Commerce) | Несколько связанных таблиц: заказы, позиции, товары, продавцы, покупатели | Основной кандидат: есть настоящий `JOIN`, регион (штат), категория, цена |
| **Mercari** (Price Suggestion) | ~1,4 млн объявлений: название, бренд, категория, состояние, цена | Кандидат №2: сильный бренд и категория |
| **Retail Price** (Retail Price Optimization) | Цена товара, категория, продажи, цены конкурентов | Возможный второй/третий датасет, небольшой |
| **Rossmann** | Продажи магазинов по дням, промо, конкуренты | Скорее временной ряд продаж, цены нет. Только в обзор |
| **Walmart** | Недельные продажи магазинов, праздники, температура, топливо | Аналогично Rossmann. Только в обзор |

> **Предварительный выбор (подтвердим на Шаге 1):** Olist (основной) + Mercari или Retail Price.
> Датасеты не имеют общего ключа, поэтому «объединение таблиц» делаем внутри каждого выбранного датасета (в Olist это настоящий `JOIN`), а выводы сравниваем между датасетами.

## 6. План работ по шагам

Работаем **постепенно**: один шаг за раз, переход к следующему по вашему сигналу. В конце каждого шага вы задаёте вопросы, я отвечаю. В каждом шаге есть строки **Отчёт** (что фиксируем в тексте) и **Git** (что коммитим).

### Шаг 0. Окружение — `[~]`
- Установить Python 3.12, создать проект в PyCharm с Virtualenv.
- Создать структуру папок, `requirements.txt`, установить зависимости.
- Мини-введение в Python для Java-разработчика.
- **Проверка:** `src/check_env.py` выводит таблицу и средние цены по брендам.
- **Отчёт:** создать каркас `reports/sections/` и `build_report.py`, собрать пустой `report.docx` с титульным листом.
- **Git:** `git init`, `.gitignore`, первый коммит `chore: init project`.

### Шаг 1. Обзор датасетов и выбор — `[ ]`
- Скачать/изучить 5 датасетов (Kaggle).
- Для каждого описать: источник, размер, поля, наличие цены, пригодность.
- Выбрать 1–3 и обосновать выбор.
- **Результат:** таблица сравнения для раздела 3 отчёта.
- **Отчёт:** раздел 3 (обзор датасетов), черновик введения (актуальность, цель, задачи).
- **Git:** коммит `docs: dataset review and selection`, тег `step-1`.

### Шаг 2. Загрузка и объединение таблиц — `[ ]`
- Загрузить данные в `DataFrame`.
- Объединить таблицы (`merge`, аналог SQL `JOIN`), проверить, что не потеряли и не размножили строки.
- Обработать пропуски, дубликаты, типы, явные выбросы.
- Сохранить результат в `data/processed/` (формат Parquet).
- **Результат:** чистые итоговые таблицы, описание пайплайна для раздела 5.
- **Отчёт:** раздел 5 (методология: объединение таблиц, очистка, схема пайплайна).
- **Git:** коммит `feat: load, merge and clean data`, затем отдельный `docs: methodology section`.

### Шаг 3. Описательная статистика — `[ ]`
- Среднее, медиана, стандартное отклонение, квантили, асимметрия.
- Распределение цены (она, как правило, скошена, поэтому смотрим и `log(price)`).
- Разбивка цены по категориям, брендам, регионам.
- **Результат:** таблицы и графики (гистограммы, boxplot).
- **Отчёт:** раздел 6.1 (описательная статистика) с таблицами и графиками.
- **Git:** коммит `feat: descriptive statistics`, затем `docs: results 6.1`.

### Шаг 4. Проверка гипотез — `[ ]`
Рабочие гипотезы (уточним после Шага 3):
- **H1:** средняя цена различается между категориями.
- **H2:** средняя цена различается между брендами (Mercari).
- **H3:** цена различается между регионами (штаты Olist).

Методы: проверка нормальности, ANOVA или Краскела-Уоллиса, post-hoc тесты (Тьюки / Данн), размер эффекта (eta²), поправка на множественные сравнения.
- **Результат:** p-value, размер эффекта, интерпретация простыми словами.
- **Отчёт:** раздел 6.2 (проверка гипотез), уточнить формулировки гипотез во введении.
- **Git:** коммит `feat: hypothesis tests`, затем `docs: results 6.2`.

### Шаг 5. Корреляции и VIF — `[ ]`
- Корреляционная матрица (Пирсон и Спирмен), тепловая карта.
- VIF для проверки мультиколлинеарности (признаки, которые дублируют друг друга).
- Решение, какие признаки убрать или объединить.
- **Результат:** обоснованный набор признаков для моделей.
- **Отчёт:** раздел 6.3 (корреляции и VIF), дополнить раздел 5 описанием отбора признаков.
- **Git:** коммит `feat: correlation and VIF`, затем `docs: results 6.3`.

### Шаг 6. Регрессия — `[ ]`
- **Линейная регрессия** — базовая модель и интерпретация коэффициентов.
- **Ridge** — то же с регуляризацией (штраф за большие коэффициенты, борьба с мультиколлинеарностью).
- **Квантильная регрессия** — прогноз не среднего, а квантилей (например, 10-й, 50-й, 90-й процентили цены).
- Разбиение train/test, кросс-валидация, метрики: MAE, RMSE, R².
- Значимые факторы: коэффициенты, p-value, важность признаков.
- **Результат:** сравнение моделей, список значимых факторов цены.
- **Отчёт:** раздел 6.4 (регрессия: сравнение моделей, значимые факторы). Можно разбить на две фиксации: линейная и Ridge, затем квантильная.
- **Git:** коммиты `feat: linear and ridge`, `feat: quantile regression`, `docs: results 6.4`.

### Шаг 7. Классификация ценового сегмента — `[ ]`
- Разбить цену на сегменты (дешёвый / средний / дорогой) по квантилям.
- Модели: логистическая регрессия и, для сравнения, дерево/случайный лес.
- Метрики: accuracy, precision, recall, F1, матрица ошибок.
- **Результат:** качество классификации, какие признаки важны для сегмента.
- **Отчёт:** раздел 6.5 (классификация ценового сегмента).
- **Git:** коммит `feat: price segment classification`, затем `docs: results 6.5`.

### Шаг 8. Отчёт и презентация — `[ ]`
- Довести DOCX до финального вида по структуре из раздела 8.
- Обзор методов (≥ 5 источников) и список литературы (≥ 10, из них ≥ 5 по методам).
- Презентация (PPTX) для защиты: проблема, данные, методы, результаты, выводы.
- Финальная проверка: код запускается с нуля, цифры в отчёте совпадают с кодом.
- **Отчёт:** разделы 4 (обзор методов), 7 (ограничения), 8 (выводы), 9 (источники), 10 (приложения), финальная вычитка.
- **Git:** коммиты `docs: methods review`, `docs: discussion and conclusions`, `feat: presentation`, тег `v1.0`.

## 7. Ведение отчёта и git параллельно с работой

Отчёт не пишем в конце одним куском: после каждого шага (или его заметной части) фиксируем результат в тексте отчёта и делаем коммит.

### Цикл «шаг → отчёт → коммит»

1. Выполнили шаг, получили таблицы, графики, числа.
2. Записали раздел отчёта в `reports/sections/NN_name.md` (обычный текст с заголовками; таблицы и картинки подключаются ссылками).
3. Запустили `python src/build_report.py`, получили обновлённый `reports/report.docx`.
4. Проверили, что числа в отчёте совпадают с выводом кода.
5. `git add` и `git commit` с понятным сообщением.

### Почему текст отчёта лежит в `.md`, а не правится прямо в Word

DOCX бинарный: в git его нельзя нормально сравнивать по версиям. Поэтому исходники отчёта (`sections/*.md`) лежат текстом, а `report.docx` собирается скриптом. Аналогия: исходники `.java` и собранный `.jar`. Сам `report.docx` тоже коммитим, чтобы всегда была готовая версия на каждом этапе.

### Правила git

| Что | Правило |
|---|---|
| Ветка | Одна `main`, для учебного проекта достаточно |
| Сообщения | Префиксы: `feat:` код анализа, `docs:` отчёт, `chore:` настройка, `fix:` исправление |
| Размер коммита | Одна логическая единица: код шага отдельно от текста отчёта |
| Теги | `step-1` … `step-8`, финальный `v1.0`, чтобы можно было вернуться к любому этапу |
| Не коммитим | `.venv/`, `data/raw/` (большие чужие датасеты), `__pycache__/`, ключи Kaggle |
| Коммитим | `src/`, `reports/`, `requirements.txt`, `README.md`, небольшие `data/processed/` по необходимости |
| Показ изменений | Перед коммитом показывать `git status` и список изменённых файлов. Пользователь должен видеть все правки |
| Пуш | `git push` — **только после явного подтверждения пользователя**. Без подтверждения не выполнять |

## 9. Правила работы

1. Один шаг за раз, без забегания вперёд.
2. Каждый шаг делим на подшаги. После каждого подшага — остановка и короткий отчёт: что сделано, какие файлы изменены, как проверено. Продолжаем только после команды «дальше».
3. Пользователь обязан видеть все изменения: никаких скрытых правок. Перед коммитом показываем список изменённых файлов и ждём подтверждения.
4. `git push` — только после явного подтверждения пользователя.
5. Весь код с комментариями и аналогиями с Java там, где это помогает.
6. Каждый шаг заканчивается проверяемым результатом (таблица, график, число).
7. Все числа в отчёте берутся только из запущенного кода.
8. Источники в списке литературы должны быть реальными, проверяемыми (ссылки, DOI).
9. Каждый шаг заканчивается обновлением отчёта и коммитом (см. раздел 7).
10. Статус шагов отмечаем в этом файле: `[ ]` не начат, `[~]` в работе, `[x]` готов.
11. Если формулировка задания или следующий подшаг непонятны — останавливаемся и разбираемся, а не угадываем.

## 10. Мини-словарь

| Термин | Простыми словами |
|---|---|
| DataFrame | Таблица в памяти с именованными колонками |
| merge | `JOIN` двух таблиц по ключу |
| Описательная статистика | Сводка данных: среднее, медиана, разброс |
| p-value | Вероятность увидеть такой результат случайно. Малое значение (< 0,05) говорит, что эффект, скорее всего, не случаен |
| Корреляция | Мера связи двух чисел от −1 до 1 |
| VIF | Показывает, насколько признак дублируется другими (больше 5–10 считается проблемой) |
| Ridge | Линейная регрессия со штрафом за большие коэффициенты |
| Квантильная регрессия | Прогноз не среднего, а заданного процентиля цены |
| train/test | Обучаем на одной части данных, проверяем на другой, как unit-тест для модели |
